# Publish Zrain Links (operator guide)

**Current status:** Hosting configuration committed. A live URL, database, custom domain, and public readiness are **not yet confirmed**. Never point visitors to a non-working placeholder URL.

## Public platform domain (first deployment)
1. Connect Render to `zrain03/zrain-links`, select the Docker web service in `render.yaml`, and provision an external **persistent PostgreSQL** database (such as Neon).
2. Set the secret environment values required by `application-prod.yml`: `DB_JDBC_URL` (JDBC URL of PostgreSQL), `DB_USERNAME`, `DB_PASSWORD`. Never commit them or paste them in public logs. For Neon, ensure SSL is enabled in the JDBC URL.
3. Keep `SPRING_PROFILES_ACTIVE=prod`. A random `ZRAIN_JWT_SECRET_BASE64` is generated by the Blueprint; **keep it durable between deployments** or existing tokens become invalid. Back it up in an appropriately protected secret manager. Never log it.
4. Set `ZRAIN_LINKS_BASE_URL` to the **actual** HTTPS domain assigned to this service (for example `https://<your-actual-service>.onrender.com`) and redeploy. Do not include a trailing slash.
5. Check deployment logs for Flyway migration success and Hibernate validation, then manually test sign-up, sign-in, short-link creation, redirect, QR, owner isolation, and persistence across restarts.
6. Confirm the server is publicly reachable before announcing the URL. A sleeping free web instance may delay redirects and login.

## Domain naming and safety
- The platform owner controls `ZRAIN_LINKS_BASE_URL`. Visitors **cannot replace** the service domain by typing an arbitrary hostname; those would not route to Zrain Links.
- Visitors already can select **customAlias** for the URL path (example `/claimmp`).
- For a platform-owned custom hostname, add and verify it in Render and at the DNS provider, enable HTTPS, then update `ZRAIN_LINKS_BASE_URL`.
- User-owned domains (example `go.customer.com`) are a **separate unfinished feature**. Implement verified domain ownership (DNS TXT challenge), host binding, automatic TLS, abuse review, isolation, and domain deletion lifecycle before offering it. The current data model does **not** implement multi-domain alias isolation.
- Do not use unvalidated user Host headers to construct the public short URL.

## Public launch blockers
The submitted Docker/Blueprint files are deployment scaffolding, not a completed live deploy or security approval. Before open registration, implement persistent-data backup/restore tests, authentication and link creation rate limits, phishing/malware reporting and abuse controls, account recovery, logging, reliability monitoring, and a manual browser regression test. A service that redirects arbitrary users can be abused; do not advertise it to general users before review.

## Local development
The local `local` profile still uses temporary in-memory H2; that is expected. Do not use the local profile on a public instance.
